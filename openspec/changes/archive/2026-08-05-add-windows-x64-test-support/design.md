## Context

현재 앱은 macOS 개발 환경에서 관리되고 있으며, Windows 전용 WebView, 트레이, 창 포커스 및 PowerShell sidecar 준비를 직접 실행해 볼 수 없다. 기존 `prepare-codex-sidecar.ps1`은 Windows x64 sidecar 이름을 준비하지만, 테스트 PC에서 개발 도구 없이 실행할 수 있는 테스트 흐름, 자동 검증, 진단 및 수동 수락 절차는 없다. 동기는 [proposal.md](proposal.md)를 따른다.

## Goals / Non-Goals

**Goals:**

- Windows x64 PC에서 설치·실행이 간단한 테스트 전용 앱을 제공한다.
- 실제 OpenAI/ChatGPT 계정 없이 UI와 Windows 창 동작을 확인할 수 있게 한다.
- 실제 계정 검증이 필요할 때도 비밀을 진단 결과나 로그에 남기지 않는다.
- Windows 네이티브 실행에서 실패 지점을 빠르게 식별하고 재현 가능하게 기록한다.

**Non-Goals:**

- 공개 릴리스, 코드 서명, 자동 업데이트 및 설치 프로그램 정책을 결정하지 않는다.
- macOS, Linux, Windows ARM64 또는 Windows x86을 지원하지 않는다.
- 테스트 모드로 OpenAI API 또는 ChatGPT/Codex 사용량의 정확성을 검증하지 않는다.

## Decisions

### 별도 테스트 빌드 진입점

Windows x64에서만 생성하는 테스트 빌드 명령과 결과물 확인 명령을 제공한다. 이 빌드는 일반 개발 실행과 구분되는 명시적 테스트 모드 표식을 포함하고 Windows x64 sidecar를 함께 검증한다.

테스트 PC에서 `tauri dev`를 실행하는 방식은 Rust, Node.js, pnpm, WebView 개발 의존성 설치를 요구하므로 채택하지 않는다. 정식 공개 배포를 지금 설계하는 방식도 범위를 넓히므로 채택하지 않는다. 테스트용으로 생성한 로컬 실행물 또는 설치형 결과물만 전달한다.

### 네트워크와 인증에서 독립적인 샘플 데이터

테스트 빌드에서는 명확히 표시된 고정 샘플 사용량을 UI에 공급한다. 이로써 트레이, 대시보드, 위젯, 창 표시·숨김과 설정 복원 같은 Windows UX는 네트워크와 계정 상태에 영향을 받지 않는다.

실제 API 응답을 녹화해 재생하는 방식은 실제 데이터 또는 구조 변화에 의존하고 민감 정보 유출 위험을 키우므로 채택하지 않는다. 테스트 모드에서 실제 API를 호출하는 방식도 비결정적이므로 채택하지 않는다.

### 진단은 최소 정보·명시적 수집 원칙

진단 화면 또는 복사 가능한 보고서는 버전, OS/아키텍처, 테스트 모드, sidecar 파일 발견 및 기동 상태, 설정 저장소 접근 상태, 오류 코드/메시지만 포함한다. API 키·OAuth 토큰·Authorization 헤더·원문 입력은 수집 대상에서 제외하며, 오류 문자열도 비밀을 포함하지 않도록 정제한다.

모든 런타임 로그를 자동으로 업로드하거나 내보내는 방식은 개인정보와 자격 증명 위험 때문에 채택하지 않는다.

### 자동 smoke test와 사람 중심의 수락 테스트 분리

Windows x64에서 실행되는 자동 검증은 빌드, sidecar 존재, 테스트 모드 기동을 빠르게 확인한다. 트레이 클릭, 창의 실제 표시 위치, 위젯 드래그, 다중 모니터 및 DPI처럼 GUI 자동화가 취약하거나 물리 환경에 의존하는 동작은 Windows 테스트 PC에서 문서화된 수동 체크리스트로 검증한다.

모든 UI를 headless 테스트로 대체하는 방식은 트레이·WebView·포커스 문제를 놓치므로 채택하지 않는다.

## Risks / Trade-offs

- [테스트 실행물이 Windows PC의 보안 정책에 의해 차단됨] → 테스트 가이드에 차단 증상과 수집할 진단 정보를 기록하고, 코드 서명 해결은 별도 배포 변경으로 분리한다.
- [테스트 모드가 운영 코드와 달라져 실제 흐름을 가림] → 테스트 모드는 데이터 공급만 대체하고, 실제 API 키와 OAuth 흐름은 별도의 수동 수락 항목으로 유지한다.
- [sidecar 설치 프로그램 또는 upstream 변화] → 준비 단계, 파일명 확인, 기동 smoke test를 Windows에서 한 묶음으로 실행한다.
- [DPI/다중 모니터 문제를 자동화가 놓침] → 최소 두 가지 배율과 보조 모니터가 있는 경우의 수동 체크리스트를 필수 수락 기준으로 둔다.

## Migration Plan

1. Windows x64에서 테스트 빌드와 smoke test를 생성한다.
2. 별도의 Windows PC에서 테스트 실행물을 실행하고 체크리스트를 완료한다.
3. 실패 시 진단 보고서와 재현 단계를 수집해 수정한 뒤, 같은 smoke test와 수동 체크리스트를 다시 수행한다.
4. 테스트 전용 진입점은 일반 사용자용 실행 흐름을 변경하지 않으므로, 문제가 생기면 해당 테스트 진입점과 테스트 모드만 제거하여 되돌린다.
