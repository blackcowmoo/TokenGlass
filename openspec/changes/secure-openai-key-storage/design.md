## Context

현재 메인 대시보드와 위젯은 각각 Tauri Store의 `settings.json`에서
`tokenglass_openai_admin_key`를 읽어 원본 키를 `fetch_openai_usage` 명령에 전달한다. Store는
앱 데이터 디렉터리에 기본 JSON 직렬화로 기록되고, 현재 macOS 설치에서 파일은
`~/Library/Application Support/com.mykim.tokenglass/settings.json`에 생성된다. 사용량 캐시는
원본 키 대신 SHA-256 지문을 보관하지만 원본 키의 영속 저장과 WebView 전달은 보호하지 못한다.

지원 대상은 Apple Silicon 및 Intel macOS, Windows x64, Linux x64이다. 일반 설정 Store는
수동 환율과 같은 비밀이 아닌 설정을 위해 계속 필요하다. 자세한 동작 계약은
`specs/secure-openai-key-storage/spec.md`를 따른다.

## Goals / Non-Goals

**Goals:**

- 세 운영체제의 네이티브 사용자 보안 저장소를 하나의 Rust 경계로 추상화한다.
- 원본 API 키의 수명을 설정 입력과 백엔드 OpenAI 요청 사이로 제한한다.
- 다중 WebView가 동시에 시작해도 마이그레이션과 캐시 무효화가 일관되게 동작하게 한다.
- 저장소 오류를 비밀이 없는 안정적인 사용자 오류로 변환하고 단위 테스트에서 OS 저장소를 대체할 수 있게 한다.
- 데이터 손실 없이 기존 평문 값을 제거하며 보안 수준을 낮추지 않는 롤백 정책을 제공한다.

**Non-Goals:**

- ChatGPT/Codex OAuth 자격 증명 저장 방식을 변경하지 않는다.
- OpenAI가 발급한 API 키 자체의 권한, 만료 또는 서버 측 회전 정책을 관리하지 않는다.
- 디스크 전체 암호화나 같은 사용자 권한의 실행 중 메모리 검사까지 방어하지 않는다.
- 이번 변경에서 전체 Tauri CSP 또는 모든 Store 권한을 재설계하지 않는다.
- 보안 저장소가 없는 환경을 위해 Stronghold 또는 평문 파일 폴백을 추가하지 않는다.

## Decisions

### Rust `keyring` 3.6 계열로 네이티브 저장소를 사용한다

`keyring` 3.6 계열을 기본 기능 없이 고정하고 대상별 기능으로 macOS Keychain,
Windows Credential Manager, Linux Secret Service를 활성화한다. Linux 암호화 구현에는
RustCrypto 기반 기능을 사용해 OpenSSL 런타임 의존성을 추가하지 않는다. 3.6 계열은 Rust 1.75
MSRV와 edition 2021을 지원하므로 현재 Tauri 2 빌드 하한을 불필요하게 높이지 않는다. 실제 적용
시 선택한 patch 버전을 `Cargo.lock`으로 고정하고 세 대상 빌드에서 확인한다.

자격 증명 식별자는 앱 전체에서 고정한다.

- service: `com.mykim.tokenglass`
- account: `openai-admin-key`

대안으로 검토한 Tauri Stronghold는 크로스 플랫폼 암호화 vault를 제공하지만 vault 비밀번호의
획득·보관·복구라는 두 번째 비밀 문제가 생긴다. OS별 SDK를 직접 호출하는 방식은 의존성을 줄일
수 있지만 오류 의미와 테스트 경계를 세 번 구현해야 한다. 단일 문자열 자격 증명에는 `keyring`
추상화가 가장 작은 유지보수 범위를 제공한다.

### 자격 증명 접근은 Rust 백엔드가 소유한다

`src-tauri/src/openai/credentials.rs`가 저장소 식별자, 오류 분류와 get/set/delete 동작을
소유한다. OS 호출은 동기 API이므로 비동기 Tauri 명령에서 blocking 작업으로 분리해 UI 런타임을
막지 않는다. 테스트에서는 동일한 계약의 메모리 구현을 주입해 플랫폼 저장소 없이 수명 주기와
마이그레이션을 검증한다.

`commands/openai.rs`는 다음 경계를 제공한다.

- `get_openai_key_status`: 마이그레이션을 확인하고 `configured` 및 비밀이 아닌 오류 상태만 반환
- `save_openai_admin_key`: 입력된 새 키를 저장하고 성공 후 캐시 무효화
- `delete_openai_admin_key`: 자격 증명을 멱등 삭제하고 캐시 무효화
- `fetch_openai_usage`: `adminKey` 인자를 제거하고 백엔드에서 저장된 키를 조회

프런트엔드는 저장된 키를 입력 필드 값으로 다시 채우지 않는다. 설정 화면은 `연결됨` 상태와 빈
교체 입력란을 보여주며 삭제는 별도 확인 가능한 버튼으로 제공한다. 위젯은 Store를 통해 키를 읽지
않고 사용량 명령만 호출한다.

대안인 프런트엔드용 보안 저장소 플러그인은 WebView에 자격 증명 읽기 권한을 다시 부여하므로
선택하지 않는다. Rust 직접 사용으로 자격 증명용 Tauri capability도 필요하지 않다.

### 보안 저장소 오류는 안정적인 공개 오류로 변환한다

플랫폼 및 라이브러리 오류는 내부 분류로 변환하고 원문 자격 증명이나 요청 payload를 로그하지
않는다. 사용자에게는 최소한 `notConfigured`, `unavailable`, `lockedOrDenied`,
`operationFailed`, `migrationFailed`를 구분할 수 있는 코드와 일반 메시지를 반환한다. 플랫폼
오류 원문은 비밀 포함 가능성을 배제할 수 없으므로 진단 및 기본 로그에 그대로 포함하지 않고,
운영체제와 작업 단계 같은 비밀이 아닌 문맥만 기록한다.

보안 저장소를 사용할 수 없으면 요청을 실패시키며 Store 또는 다른 파일에 자동 저장하지 않는다.
세션 전용 키 모드는 저장 성공처럼 오인될 수 있고 새 상태 수명을 추가하므로 이번 변경에는 넣지
않는다.

### 마이그레이션은 보안 저장소 우선의 직렬화된 초기화로 수행한다

메인 화면이 시작 시 호출하는 상태 조회와 위젯의 사용량 조회가 공통 `ensure_migrated` 경계를
통과한다. 프로세스 상태의 mutex로 여러 WebView의 동시 실행을 직렬화하며 결과가 확정된 뒤 같은
실행에서 중복 작업을 피한다.

1. 보안 저장소에 값이 있으면 이를 권위 있는 값으로 선택한다.
2. 이때 legacy Store 값도 있으면 보안 저장소 값을 덮어쓰지 않고 legacy 항목을 삭제·저장한다.
3. 보안 저장소가 비어 있고 legacy 값이 있으면 보안 저장소에 기록한다.
4. 즉시 다시 읽어 입력과 일치함을 확인한다.
5. 확인 후에만 legacy 항목을 `delete`하고 Store를 저장한다.

기록 또는 확인 실패 시 legacy 값은 유지한다. 보안 저장은 성공했지만 legacy 정리가 실패하면
보안 저장소를 계속 권위 있는 값으로 사용하고 다음 실행에서 정리를 재시도한다. 별도 완료 marker는
보안 저장소와 legacy 값의 실제 존재 상태보다 쉽게 어긋날 수 있으므로 추가하지 않는다.

### 키 변경은 저장 성공 후 캐시를 무효화한다

현재 캐시의 SHA-256 지문 격리는 유지한다. 새 키 저장 또는 삭제가 성공한 경우
`OpenAiUsageState`의 캐시를 명시적으로 비운다. 새 키 저장이 실패하면 기존 자격 증명과 캐시를
그대로 유지한다. 이 순서는 사용 가능한 기존 연결을 저장 실패 때문에 잃지 않게 한다.

## Risks / Trade-offs

- [Linux 데스크톱에 Secret Service 또는 사용자 D-Bus 세션이 없을 수 있음] → 평문 폴백 없이
  `unavailable`을 반환하고, 지원 문서와 Linux 수동 검증에 서비스 존재·잠금·부재 사례를 포함한다.
- [macOS Keychain 또는 Linux keyring이 사용자 확인이나 잠금 해제를 요구할 수 있음] → 호출을
  blocking 작업으로 격리하고 취소·거부를 비밀 없는 상태로 표시한다.
- [OS 자격 증명은 앱 제거 후 남을 수 있음] → 앱 내 명시적 삭제를 제공하고 지원 문서에 제거
  방법을 기록한다. 제거 프로그램에서 사용자 비밀을 자동 삭제하는 것은 이번 범위에서 제외한다.
- [마이그레이션 중 프로세스 종료로 두 저장소에 값이 남을 수 있음] → 보안 저장소를 우선하고 다음
  실행에서 legacy 값만 정리하는 멱등 절차를 사용한다.
- [의존성의 플랫폼별 빌드가 기존 Windows/macOS/Linux 패키징을 깨뜨릴 수 있음] → 기본 기능을
  끄고 필요한 backend만 선택하며 각 지원 target의 빌드 또는 실기기 smoke 결과를 요구한다.
- [원본 키는 요청 중 Rust 메모리에 존재함] → 소유 범위를 자격 증명 모듈과 HTTP 요청으로
  제한하고 Debug 출력, 직렬화, 영속 캐시를 금지한다. 프로세스 메모리 공격 방어는 비목표다.
- [현재 `csp: null`과 광범위한 `store:default` 권한은 별도 공격면임] → API 키를 Store에서
  제거해 이 변경의 비밀 노출을 차단하고, CSP 및 비밀 아닌 Store 권한 축소는 후속 보안 작업으로
  추적한다.

## Migration Plan

1. 자격 증명 저장소 경계, 공개 오류, 메모리 테스트 구현을 먼저 추가한다.
2. 보안 저장소 명령과 마이그레이션을 연결하되 기존 프런트엔드 읽기 경로는 아직 제거하지 않는다.
3. 마이그레이션 성공·실패·중복 실행 테스트를 통과시킨다.
4. 메인 화면과 위젯을 새 상태·사용량 명령으로 전환하고 Store의 키 읽기·쓰기를 제거한다.
5. 진단, 오류, 캐시와 `settings.json`을 canary 키로 검사한다.
6. macOS, Windows x64, Linux x64에서 네이티브 저장·갱신·삭제와 legacy 이전을 확인한다.
7. 검증 완료 후 배포하며, 기존 사용자는 첫 실행 시 자동으로 이전된다.

롤백 시 보안 저장소 값을 평문 Store로 자동 복원하지 않는다. 이전 버전은 보안 저장소를 읽지
못하므로 사용자가 키를 다시 입력해야 한다. 이는 가용성보다 비밀을 다시 평문으로 만들지 않는
보안 원칙을 우선한 의도적인 제약이다.
