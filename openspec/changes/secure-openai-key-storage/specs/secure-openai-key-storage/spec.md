## Purpose

OpenAI 조직 관리자 API 키를 지원 운영체제의 사용자 보안 저장소에서 일관되게 관리하고,
저장·사용·이전·삭제 과정에서 원본 비밀이 일반 설정이나 관찰 가능한 출력에 노출되지 않도록
보장한다.

## ADDED Requirements

### Requirement: 운영체제 보안 저장소에 API 키 영속화

시스템은 OpenAI 조직 관리자 API 키를 macOS에서는 Keychain, Windows에서는 Credential
Manager, Linux에서는 Secret Service에 저장해야 하며(MUST), 일반 설정 파일이나 별도의 평문
파일에 영속화하지 않아야 한다(MUST).

#### Scenario: 지원 운영체제에서 키 저장

- **WHEN** 사용자가 유효한 비어 있지 않은 API 키를 저장한다
- **THEN** 시스템은 현재 운영체제의 사용자 보안 저장소에 해당 키를 영속화하고 연결됨 상태를 표시해야 한다

#### Scenario: 보안 저장소를 사용할 수 없음

- **WHEN** 운영체제 보안 저장소가 없거나 잠겼거나 사용자 세션에서 접근할 수 없다
- **THEN** 시스템은 키 저장을 실패로 처리하고 평문 영속 저장소로 폴백하지 않으며 사용자가 조치할 수 있는 비밀 비포함 오류를 표시해야 한다

### Requirement: 원본 키의 백엔드 전용 사용

시스템은 키 저장 명령이 새 값을 입력받는 경우를 제외하고 원본 API 키를 WebView에 반환하거나
프런트엔드가 호출하는 사용량 조회 명령의 입력으로 요구하지 않아야 한다(MUST). 프런트엔드에는
키의 저장 여부만 공개해야 한다(MUST).

#### Scenario: 저장된 키로 사용량 조회

- **WHEN** 메인 대시보드 또는 데스크톱 위젯이 OpenAI 사용량을 요청한다
- **THEN** 백엔드는 보안 저장소에서 키를 읽어 요청에 사용하고 원본 키를 프런트엔드 응답에 포함하지 않아야 한다

#### Scenario: 연결 상태 조회

- **WHEN** 프런트엔드가 OpenAI 연결 상태를 요청한다
- **THEN** 시스템은 저장된 키의 존재 여부와 비밀이 아닌 상태만 반환하고 키 원문이나 일부를 반환하지 않아야 한다

### Requirement: 명시적인 키 갱신 및 삭제

시스템은 새 API 키 저장과 기존 API 키 삭제를 구분된 동작으로 제공해야 하며(MUST), 성공한 갱신
또는 삭제 후 이전 키에 연결된 사용량 캐시를 제공하지 않아야 한다(MUST).

#### Scenario: 기존 키 갱신 성공

- **WHEN** 사용자가 새 API 키를 저장하고 보안 저장소 쓰기가 성공한다
- **THEN** 시스템은 이전 키의 캐시를 무효화하고 새 키를 사용해 다음 사용량 조회를 수행해야 한다

#### Scenario: 기존 키 갱신 실패

- **WHEN** 새 API 키를 저장하는 동안 보안 저장소 쓰기가 실패한다
- **THEN** 시스템은 기존에 저장된 키와 연결 상태를 유지하고 새 키 또는 기존 키를 오류에 포함하지 않아야 한다

#### Scenario: 키 삭제

- **WHEN** 사용자가 저장된 API 키 삭제를 요청한다
- **THEN** 시스템은 보안 저장소의 자격 증명과 관련 캐시를 제거하고 연결되지 않음 상태를 표시해야 한다

#### Scenario: 이미 없는 키 삭제

- **WHEN** 저장된 자격 증명이 없는 상태에서 삭제를 다시 요청한다
- **THEN** 시스템은 작업을 성공한 멱등 삭제로 처리하고 연결되지 않음 상태를 유지해야 한다

### Requirement: 기존 Store 키의 안전한 1회 마이그레이션

시스템은 기존 `settings.json`에 `tokenglass_openai_admin_key` 값이 있고 보안 저장소에 키가 없는
경우 이를 한 번 마이그레이션해야 하며(MUST), 보안 저장소에 기록한 값을 확인한 후에만 Store의
원본 값을 삭제해야 한다(MUST).

#### Scenario: 기존 키 마이그레이션 성공

- **WHEN** 앱 시작 시 기존 Store 키가 있고 보안 저장소에는 키가 없다
- **THEN** 시스템은 키를 보안 저장소에 기록하고 다시 읽어 일치함을 확인한 뒤 Store에서 원본 키를 삭제하고 저장해야 한다

#### Scenario: 보안 저장소 기록 실패

- **WHEN** 기존 Store 키를 보안 저장소에 기록하거나 확인하는 작업이 실패한다
- **THEN** 시스템은 데이터 손실을 막기 위해 기존 Store 키를 유지하고 마이그레이션 실패 상태를 비밀 없이 표시해야 한다

#### Scenario: 보안 저장 후 Store 정리 실패

- **WHEN** 보안 저장소 기록과 확인은 성공했지만 기존 Store 키 삭제 또는 저장이 실패한다
- **THEN** 시스템은 보안 저장소의 키를 권위 있는 값으로 사용하고 다음 앱 시작 시 Store 정리를 다시 시도해야 한다

#### Scenario: 보안 저장소와 기존 Store에 모두 키 존재

- **WHEN** 앱 시작 시 보안 저장소와 기존 Store 양쪽에 키가 존재한다
- **THEN** 시스템은 보안 저장소의 값을 변경하지 않고 기존 Store의 원본 키만 삭제해야 한다

### Requirement: 비밀 비노출

시스템은 API 키 원문을 진단 정보, 사용자에게 표시되는 상태와 오류, 애플리케이션 로그, 설정
내보내기 또는 사용량 캐시 데이터에 포함하지 않아야 한다(MUST). 캐시 격리에 키 식별자가 필요한
경우 원본 키를 복원할 수 없는 지문만 앱 프로세스 메모리에 보관해야 한다(MUST).

#### Scenario: 진단 정보와 오류 수집

- **WHEN** 키 저장, 조회, 마이그레이션 또는 OpenAI 요청이 실패하고 사용자가 진단 정보를 확인하거나 복사한다
- **THEN** 화면, 복사된 진단 문자열 및 로그에는 API 키 원문이 포함되지 않아야 한다

#### Scenario: 사용량 캐시 생성

- **WHEN** 저장된 키로 OpenAI 사용량 조회가 성공하여 캐시가 생성된다
- **THEN** 캐시에는 API 키 원문이 포함되지 않고 키 격리에 필요한 비가역 지문만 메모리에 존재해야 한다

#### Scenario: 설정 파일 검사

- **WHEN** 새 설치 또는 마이그레이션이 완료된 설치의 일반 설정 파일을 검사한다
- **THEN** 파일에는 OpenAI 조직 관리자 API 키나 해당 키를 복구할 수 있는 값이 없어야 한다
