## Context

현재 `fetch_openai_usage` Tauri 명령은 호출마다 OpenAI Usage API와 Costs API를 순차적으로 요청하고 집계 결과만 반환한다. `App.tsx`는 시작 시 및 수동 동작에서 이 명령을 호출하고, `Widget.tsx`는 별도의 5분 타이머로 같은 명령을 호출하므로 두 WebView가 요청과 성공 시각을 공유하지 못한다. 메인 창은 포커스를 잃으면 종료되지 않고 숨겨지므로 앱 실행 중 갱신 트리거로 계속 사용할 수 있다.

관련 사용자 동작은 `specs/openai-usage-refresh/spec.md`에 정의되어 있다.

## Goals / Non-Goals

**Goals:**

- 하나의 Tauri 프로세스에서 모든 WebView가 동일한 OpenAI 사용량 스냅샷을 공유한다.
- 캐시 판정과 실제 성공 시각의 기준을 Rust 백엔드에 모아 화면별 불일치를 방지한다.
- 중복 네트워크 호출을 합치면서 수동 강제 갱신의 의미를 보존한다.
- 갱신 오류가 있어도 현재 실행에서 확보한 마지막 성공 데이터를 화면에 제공한다.
- API 키 원문이나 사용량 결과를 캐시 목적으로 영속 저장하지 않는다.

**Non-Goals:**

- 앱 재시작 사이에 사용량 결과를 복원하는 영속 캐시
- 사용자가 자동 갱신 주기를 설정하는 기능
- ChatGPT/Codex 구독 사용량에 동일한 캐시 정책을 적용하는 작업
- 백그라운드 운영체제 서비스나 앱 종료 후 예약 갱신
- OpenAI Usage/Costs API 페이지네이션 또는 응답 계약 검증 개선

## Decisions

### 1. Tauri 관리 상태에 메모리 캐시를 둔다

Rust 백엔드에 `OpenAiUsageState`를 Tauri 관리 상태로 등록한다. 상태는 단일 캐시 항목과 갱신 직렬화를 위한 비동기 잠금을 보유한다. 캐시 항목은 사용량 데이터, API 키 식별자, 마지막 성공 시각, 내부 세대 번호를 포함한다.

프런트엔드별 캐시나 Tauri Store 영속 캐시도 고려했지만, 프런트엔드 캐시는 WebView 간 중복 요청을 막지 못하고 영속 캐시는 비용·사용량 정보를 디스크에 남기며 앱 시작 시 최신 조회라는 정책과 맞지 않는다.

API 키 원문은 캐시 키로 보관하지 않는다. 메모리에서만 사용하는 SHA-256 식별자를 계산하고 직렬화·로그·진단 정보에 노출하지 않는다. 이를 위해 Rust에 `sha2` 직접 의존성을 추가한다.

### 2. Tauri 명령은 데이터와 갱신 메타데이터를 함께 반환한다

`fetch_openai_usage`는 `adminKey`와 `forceRefresh`를 입력받고 다음 개념을 포함하는 스냅샷을 반환한다.

- 기존 `OpenAiUsage` 집계 데이터
- `fetchedAt`: Usage와 Costs 조회 및 파싱이 모두 성공한 시각
- `source`: `network` 또는 `cache`
- `stale`: 요청한 갱신을 완료하지 못해 마지막 성공 데이터를 반환했는지 여부
- `refreshError`: stale 응답을 만든 최근 갱신 오류

캐시가 없는 최초 조회 실패는 기존처럼 명령 오류를 반환한다. 같은 API 키의 캐시가 존재하는 후속 조회 실패는 성공 응답 안에 stale 스냅샷과 오류를 함께 반환한다. 이 계약을 사용하면 새로 열린 위젯도 백엔드의 마지막 성공 데이터를 표시할 수 있다.

별도의 `get_cached_usage`와 `refresh_usage` 명령으로 나누는 방안도 고려했지만, 호출자가 두 단계의 경쟁 상태와 실패 처리를 조정해야 하므로 단일 명령이 더 일관된 계약을 제공한다.

### 3. 5분 TTL과 단일 갱신 게이트를 사용한다

일반 요청은 동일한 API 키의 캐시가 마지막 성공 후 5분 이내이면 즉시 반환한다. 캐시가 없거나 만료됐거나 `forceRefresh`가 참이면 갱신 게이트를 획득한 뒤 캐시 상태를 다시 확인하고 필요한 경우에만 네트워크 요청을 수행한다.

각 요청은 게이트 대기 전에 현재 캐시 세대 번호를 기억한다. 대기 중 같은 API 키에 대한 다른 요청이 갱신을 완료해 세대 번호가 증가했다면, 강제 갱신 요청도 새 결과를 재사용한다. 따라서 동시에 발생한 수동·자동·위젯 요청은 하나의 갱신으로 합쳐지면서, 수동 요청 이전부터 존재하던 캐시는 우회한다.

네트워크 I/O 동안 일반 캐시 상태 잠금은 유지하지 않고 갱신 게이트만 유지한다. 짧은 상태 읽기/쓰기와 장시간 API 요청을 분리해 다른 호출자가 잠금 상태를 안전하게 관찰할 수 있도록 한다.

### 4. 프런트엔드는 공통 스냅샷 계약을 사용한다

공유 TypeScript 타입을 두어 `App.tsx`와 `Widget.tsx`가 같은 응답 계약을 사용한다. 메인 대시보드는 다음 시점에 일반 갱신을 요청한다.

- 저장된 API 키를 불러온 직후
- 5분 자동 갱신 타이머
- 숨겨졌던 메인 창이 다시 활성화될 때

수동 새로고침과 API 키 저장 후 동기화만 `forceRefresh: true`를 전달한다. 위젯은 시작 시와 기존 5분 타이머에서 일반 갱신을 요청한다. 두 타이머가 겹쳐도 백엔드 TTL과 갱신 게이트가 중복 호출을 막는다.

갱신 실패 시 프런트엔드는 기존 `usage` 상태를 `null`로 만들지 않는다. stale 스냅샷이면 데이터와 `fetchedAt`을 유지하면서 오류를 표시하고, 캐시가 없는 최초 오류일 때만 데이터 없는 오류 상태를 표시한다.

### 5. 성공 시각은 백엔드가 생성하고 화면이 현지화한다

`fetchedAt`은 두 OpenAI 응답을 모두 성공적으로 처리한 뒤 Unix epoch seconds로 기록한다. 프런트엔드는 이를 사용자 로컬 시간 형식으로 변환해 표시한다. 캐시 적중, 화면 렌더링, 실패한 갱신은 이 값을 바꾸지 않는다.

프런트엔드에서 `new Date()`를 기록하는 기존 방식은 캐시 적중도 새 성공으로 오인하므로 제거한다.

## Risks / Trade-offs

- [5분마다 메인과 위젯 타이머가 모두 실행될 수 있음] → 백엔드 TTL 재검사와 단일 갱신 게이트로 외부 호출은 하나로 제한한다.
- [OpenAI API 응답이 느리면 후속 요청이 갱신 게이트에서 대기함] → 기존 HTTP 오류/타임아웃 처리를 유지하고, 대기 요청은 완료된 캐시 세대를 재사용한다.
- [갱신 실패 후 데이터가 실제 최신 상태가 아닐 수 있음] → stale 상태, 오류, 마지막 성공 시각을 함께 표시해 데이터 신선도를 숨기지 않는다.
- [API 키 식별자 해시가 메모리에 남음] → 원문은 캐시 상태에 저장하지 않고 해시는 앱 종료 시 폐기하며 외부 응답이나 로그에 포함하지 않는다.
- [프런트엔드 타이머는 절전이나 플랫폼 스케줄링으로 지연될 수 있음] → 메인 창이 다시 활성화될 때 일반 갱신을 추가로 요청하고 백엔드가 TTL을 판단한다.

## Migration Plan

1. 기존 OpenAI API 호출 및 집계 로직을 네트워크 갱신 함수로 분리한다.
2. Tauri 관리 상태와 스냅샷 응답 계약을 추가하고 기존 명령을 캐시 인식 명령으로 전환한다.
3. 메인 대시보드와 위젯을 새 공통 타입 및 갱신 계약으로 함께 전환한다.
4. 캐시 상태 전이와 UI 빌드를 검증한 후 패키징 환경에서 시작·숨김/표시·위젯 동시 실행을 확인한다.

변경은 저장 데이터 형식을 수정하지 않으므로 데이터 마이그레이션이 필요 없다. 롤백 시 프런트엔드 호출 계약과 Rust 명령을 이전 형태로 함께 되돌리면 되며, 메모리 캐시는 앱 종료와 함께 제거된다.
